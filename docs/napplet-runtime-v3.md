# Common napplet runtime v3 on Android

Android source build 67 (0.9.39) adds this runtime. Source/device fixture validation
alone does not establish signed release or Zapstore availability.

Workspace Apps discovers common cartridges in the existing NStack
workspace → Ambulando application → stable napplet namespace. Legacy File v1/v2
apps and tracker history keep their existing paths. Apps are arbitrary HTML
bundles; routine compatible app code updates do not require another Android build.

The frozen manifest and bridge contract matches the web and Swift runtime:
`version:3`, stable `napplet_id`, `bundle_version`, `title`, `icon`,
`runtime:{protocol:3,min_host}`, named `collections`, and `capabilities`.
Exact shared manifest/request fixtures live in `core/src/test/resources/napplet-runtime-v3`.
The reference cartridge was generated by the common web `collectionCartridge`
generator; Android's instrumented test uses the same HTML with IDs generated after
its host build. The API contract is NStack `docs/contract/napplet-runtime-v1.md`.

## Trust and transport

The authenticated installation binds publisher, audience, manifest and immutable
File/version/SHA-256. The host reads audience-bound `/bundle` bytes, checks the
2 MiB limit, strict UTF-8, digest and exact manifest before mounting. An HTML
publisher claim never establishes authority. One installation exists per stable
ID/workspace/application. Reinstall reads removed metadata and uses its exact
current revision to reconnect retained collections.

All requests pass through the existing workspace SyncEngine, pinned Tower origin,
application and signer, including FIPS when already configured. Native views observe
an identity-scoped online projection. Successful mutations require exact revision
increments and server-confirmed local projection; where `get` is declared a fresh
server readback also verifies the acknowledgement. Uncertain mutations are never
automatically retried. Offline editing and background execution are unsupported.

The private WebView has an opaque origin, no network/storage/File access, no
native reflection bridge and no signer, `window.nostr` or credentials. Bridge
messages have a random per-frame nonce, strict fields, declared operations, bounded
JSON and unique request IDs. One operation runs at a time with a 45-second deadline.

## Access and updates

Device approval covers backend/service/workspace/application/viewer/stable ID,
authenticated publisher, collection scopes/schema/operations and capability
versions/operations/resources. Code digest, bundle version and presentation do not
broaden access. Compatible code updates load automatically. Unsaved inputs defer
replacement; saving or explicitly closing/discarding allows the new bundle to load.
A normal background/resume keeps the hidden frame and revalidates before showing
it. An interrupted request is labelled uncertain; users must reload before retrying.
Lock, identity/workspace changes or lost authority destroy the frame and clear its
private projection.

Audience discovery/open and collection data grants are separate. Access and data
lets authorized users change the audience, explicitly choose an authorized
collection, and replace owner-managed read/write grants. Team collections are
created private; there is no implicit workspace sharing. Personal collections prefer
the acting owner's dataset; ambiguous authorized datasets require explicit selection.
Used collection identity, schema, revision and grants are periodically revalidated.

Expanded server releases remain pending until a manager approves their declarations.
Device access review remains separate. Declining keeps the server's current active
release. Unsupported personal capabilities produce an explicit compatibility message;
Nostr DM read, decrypt, send, plaintext persistence and agent access are all unsupported.
There is no ambient signer access. Android does not offer a release rollback UI or
claim audience access to old private source File bytes.

## Removal and legacy import

Removal offers keep data or delete data. Delete requires exact stable-ID confirmation
and server authority over every affected collection; it removes collection payloads
and history, never source Files/history. Keep reconnects the same collection on
reinstall. Removing an app forgets its device approval.

Explicit import reviews a readable immutable JSON File from the viewer's self
conversation and requires confirmation that the receiving app supports the entire
object format. It imports one `legacy-snapshot` record into the acting owner's
personal collection with immutable source provenance. It is create-only; conflicts
never overwrite existing records. Original Files and every original version remain.
Automatic tracker conversion, incompatible transformations and large imports are
unsupported.

## Validation boundaries

Protocol/authority tests cover the shared fixtures, strict envelopes, safety limits,
access subsets, publisher and identity-bound approval. Synthetic Sync tests cover
signed requests, two unknown apps, isolated records, CAS, code updates/history,
keep/reinstall/delete, bad namespace/digest/revision and uncertain-write handling.
Instrumented checks exercise actual native Apps, approval and WebView controls with
post-build IDs and unchanged host bytes. A separate opt-in broker-backed live API
check must be labelled separately from native login/device and store-upgrade proof.
A source commit or debug fixture pass does not establish Zapstore delivery.
