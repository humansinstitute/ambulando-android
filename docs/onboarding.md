# Invited hosted-workspace onboarding (Android)

Existing-identity guided setup of a hosted workspace against NStack's `/api/v4/onboarding` routes. The person must already
have an unlocked identity on this device; setup is signed with it. Source of the contract: NStack
`docs/contract/onboarding-v1.md`. The Apple clients implement the same state machine.

Code: `core/.../onboarding/*` (models, invite parsing, draft store, signed API client, resumable controller; JVM-testable) and
`app/.../ui/onboarding/OnboardingScreens.kt` (Compose wizard), `app/.../OnboardingHost.kt` (per-origin/identity controller cache).
Entry points: Connect → "I have an invitation to a hosted workspace", and Settings → Hosted workspace.

## What the wizard does

1. Choose the NStack (typed, or suggested by an `https` invitation link that the person confirms). The Tower's public
   descriptor must name that same HTTPS origin before anything is signed. FIPS endpoints are refused.
2. Name, funding (US$21 minimum, presets 21/50/100 or custom up to US$10,000), optional agent from `GET /agent-offers`
   (the catalogue is empty by default), invitation code. A review screen is the gate before any side effect.
3. Continue → open owner account → create intent (claims an invitation seat) → card checkout in Stripe test mode in the
   system browser. The app never marks anything paid: it polls/refreshes `GET /intents/{id}` on return, on foreground and every
   few seconds while a payment is open, and only a server-verified funded intent unlocks provisioning.
4. Provision (`POST /intents/{id}/provision`), repeatable; a stopped step keeps payment and finished steps.
5. Honest landing: workspace created; General and agent only claimed from recorded server steps. A selected agent is shown as
   "chosen but not running".

## Safety rules (tested against an in-process strict NIP-98 fake)

- Every mutation carries a NIP-98 `payload` hash of the exact body, including bodiless ones (`{}`).
- Replay keys (`createKey`, `checkoutKey`), the invite, the review digest and the checkout order binding are written to disk
  **before** the request that depends on them. A failed write stops the operation (`PERSISTENCE`); memory only changes after a
  successful write. This includes edits/review of an existing intent, the options update, the checkout request, the order
  binding (before the browser opens) and the write that records the intent id.
- Lost answers are replayed with the same key; a changed body rotates the key but first looks for the earlier attempt by name.
- Each signature is bound to the expected npub before signing (vault must be unlocked as that identity) and on the returned
  event; an identity switch during any await signs nothing.
- Drafts are per (origin, signer), hashed file names, no-backup storage, removed with the identity. The invitation code leaves the
  draft as soon as the intent exists and is never in a URL, log, `toString` or analytics.
- Checkout URL must be https `*.stripe.com`, mode `test`, amount equal to the intent's; otherwise nothing is opened.
- Return URL comes from the NStack's authenticated `GET /onboarding/config` (`card.return_urls`, its own `HOSTING_STRIPE_RETURN_URLS`); the app uses the first valid plain-https member and the server still accepts only an exact allowlist member.

## Gated, not hidden

| Feature | State | Why |
|---|---|---|
| Card checkout | Offered only when `GET /onboarding/config` says `card.available` (test mode) and lists a valid return address | The NStack's operator allowlist (`HOSTING_STRIPE_RETURN_URLS`) is the authority; the app only insists the chosen member is plain https with no credentials, query or fragment (loopback http only in tests) |
| Lightning | Offered in the wizard and for repeat top-ups only when `GET /onboarding/config` says `lightning.available` (and onboarding is enabled) | The deployment's trusted provider is the authority; no provider exists in this repository's fixtures except a synthetic fake |
| Onboarding writes | Config `onboarding_enabled:false` or `503 onboarding_rollout_disabled` is shown as "switched off, progress kept" | `ONBOARDING_ENABLED` is a reviewed activation |
| Older NStack without the config route | Card stays off with the friendly text | Nothing is guessed |
| Sample data / family build | Explained, not offered | No real NStack |
| Payment for a key this app generated | Off until NStack confirms a hosted, proven backup | See below |

Funding bounds shown in the form come from the config (`funding.min_cents/max_cents`), falling back to US$21 .. US$10,000 only when the route is absent.

## New identity: hosted encrypted backup (mandatory before payment)

Contract: NStack `docs/contract/hosted-identity-backup-v1.md`. Code: `core/identitybackup/*`, UI `HostedBackupScreens.kt`, `IdentityScreens.kt`.

- **Origin.** A key generated by this app is "new"; imports and recoveries are "existing". `IdentityOriginStore` writes a "creating" mark before the key exists, so a crash between key creation and bookkeeping still settles to "new" (a vault that exists with that mark was made here). Importing or recovering clears it. Nothing recorded means existing, which is never gated. NStack cannot attest this: `identity_origin:"new"` on the intent is a client-declared guardrail.
- **Password.** At least 16 characters (NFKC code points) when creating (recovery accepts any password an older backup used), refused when too simple or built from the username, entered twice, used only on this phone. Defaults: scrypt log_n 16 (server accepts 16..18); read ceiling 18. NStack never checks strength.
- **Save order.** Validate locally, encrypt with `Nip49` in the vault (the vault proves the result decrypts to the same public key before returning it), write the ciphertext and CAS value to disk, only then `PUT /identity-backup/{username}` (owner-signed, `expected_revision "0"` or the stored revision). A lost answer is reconciled by asking first (`GET /me`), never by a blind second write.
- **Confirmed means proven.** The copy counts only after a signed `/me` names the username, the public ciphertext and revision equal what was uploaded, and it decrypts with the person's password to exactly this identity; the confirmation is then written durably, and memory changes only after that write. Any exception leaves the stage as whatever is durable on disk. The record is keyed to the exact NStack origin and identity; a confirmation on one origin unlocks nothing on another.
- **Payment gate.** Before account, intent, seat or checkout, a new key asks NStack again (`me()` plus the public ciphertext must still equal the proven one). A local flag alone never opens it. The server also refuses with `409 identity_backup_required`, shown the same way.
- **File copy.** After confirmation the person may also save the ciphertext (never a key or password) to a file via the system document picker; the app reads it back to check.
- **Warnings.** The no-reset / lost-password / lost-backup warning is shown in full before the password fields, with an explicit acknowledgement, before any funding. The UI also states that anyone can fetch the locked copy by username and guess offline (residual risk in the contract).
- **Recovery.** On a device with no identity: NStack address + username + password. The app reads the public ciphertext (unsigned, bounded, shape-checked before Bech32), decrypts locally (cost ceiling 18, wrong password == tamper), seals the key under a new PIN and never replaces an existing identity. No password, PIN or key is ever sent.
- **No logs/copy of secrets.** Password fields are cleared after every attempt and never saved in instance state; the ciphertext is the only thing persisted. JVM strings cannot be guaranteed wiped; the byte arrays the app owns are zeroed.

## Initial Lightning payment

Contract: NStack `POST /intents/{id}/lightning/quote` (body exactly `{idempotency_key}`; the USD amount is the intent's own `funding_cents`) and `POST /intents/{id}/lightning/quotes/{quoteId}/refresh` (empty signed body; NStack re-polls its provider and returns the quote plus the current intent). Code: `OnboardingController.requestQuote/pollQuote`, shared `TopupQuote`, UI `AwaitingLightningStep` and `LightningInvoice`.

- **One method per setup.** The method (card or Lightning) is saved in the draft *before* its first request. While a payment of one method may be payable, or its answer was lost, the other is refused locally and nothing is sent. A draft from before methods were tracked that is past review with an intent is bound to card on load (a checkout may have been requested); only NStack frees it.
- **Order of durable writes.** method + quote key + intent id + amount, then the request, then the quote id, then the invoice is shown. A lost reply, a relaunch or a failed save can only replay the same key (NStack answers with the same quote). A quote answer for another intent or amount, or a non-UUID id, is never bound or shown.
- **What frees an attempt.** (1) A refusal of the *first* request with a code NStack gives before it creates anything (`invalid_quote_request`, `intent_not_found`, `intent_not_open`, `identity_backup_required`, `onboarding_rollout_disabled`; card: `invalid_checkout`, `return_url_not_allowed`, `invalid_return_url` plus the same). A refused *replay* proves nothing about the first request and never frees it. `lightning_unavailable` is deliberately not on the list: it can follow the quote insert. Unknown 4xx/5xx or malformed answers keep the method and key. (2) A refresh in which NStack reports the quote `expired` or `cancelled` on an open, unfunded intent. (3) A cancelled intent, which NStack only allows after the provider has settled the hold. (4) The person's explicit release (below). The device clock, a wallet hand-off or a quote `settled` hint never free or fund anything; `late_payment`/`mismatch` stay held for support.
- **Money.** Only the intent NStack returns (`funded` and not reversed) means paid. Provisioning is never started by the app after payment, and no agent is started or woken.
- **Backup gate.** A key this app generated may not create an account, intent or quote until NStack holds its backup.
- **Identity.** Every signature is bound to the npub; after the quote or refresh answer the identity is checked again before anything is applied or shown. All state operations run under the controller's single mutex.
- **Display.** Sats, expiry, invoice text (only if plain bech32), copy, and "Open in wallet" (`lightning:<invoice>`). There is no QR image: the app has no QR encoder and none was added.

### Canonical payment attempt (`intent.payment_attempt`)

NStack keeps one outstanding payment per intent across devices, keys and methods and reports it on every intent (`null` = none; the field absent = an older NStack, which is *unknown*, never proof). The app adopts it into the durable draft so a new device resumes without the original key and without a new review: card resumes by asking checkout with a fresh key (NStack returns the same order, `reused`), Lightning shows the same quote. Ambiguous (more than one), contradicting this device's binding, or a different amount fail closed: nothing new is sent. `409 payment_attempt_outstanding|ambiguous` (which carry the attempt) never create anything and are adopted as such. An empty hint on an ordinary read frees **nothing**, not even a binding with no order or quote id: that request may still be in flight or the read stale, so the method and key stay and only the same key is replayed. `resume: support` (late/inconsistent payment, ambiguous, or a contradicting attempt) closes every payment action for both methods: the screen shows status only, never an invoice, wallet hand-off or new request. "Use a different payment method" calls `POST /intents/{id}/payment-attempt/release`: NStack's provider settles the payment (paid funds the setup; open is cancelled) and only that explicit release answered with no attempt (or NStack's provider-verified `expired`/`cancelled` quote on a refresh) frees the method; nothing is ever released automatically. Against an older NStack without the route the release is reported as unsupported.

## Repeat top-ups

`TopupController` + `TopupScreens.kt` (Settings › Hosted workspace › Add credit): `GET /topups`, `POST /topups/checkout`, `POST /topups/lightning/quote` `{idempotency_key, amount_cents}` and `POST /topups/lightning/quotes/{id}/refresh` (empty signed body). No intent, workspace, invitation seat or introduction is touched, and no agent is started or woken: a chosen agent stays off until the person sends its first request.

Attempt guard (card and Lightning share it):
- The draft is saved **as submitted** (method, amount, key, return address) before the request. From then until NStack itself resolves the attempt, amount, method and key are frozen: a lost reply, a failed order/quote save, an edit or a relaunch can only replay the **same key**, which NStack answers with the same order or quote. Switching card <-> Lightning is refused with the first still open.
- The attempt is freed only by NStack's word: the order leaves `pending_checkout`, or the quote reads `settled`/`expired`/`cancelled` after a server-side refresh; or by a refusal NStack gives before it creates anything (`invalid_checkout`, `return_url_not_allowed`, `invalid_quote_request`, `too_many_open_topup_quotes`, account/rollout refusals). Network errors, 5xx and `lightning_unavailable` (which can follow the quote insert) never free it. The device clock never does.
- The order id / quote id is saved before the browser opens or the invoice shows. A quote for another amount or with an intent is never bound or shown.
- A saved attempt that is present but unreadable (corrupt, wrong identity or version) fails closed: no request, no new key, and the file is never overwritten. Only an absent file means "no attempt".
- Lightning: the invoice is shown only if it is plain bech32 text; copy and "Open in wallet" (`lightning:<invoice>`) use that validated text. The screen shows sats, expiry, and the safe states: payable, past expiry (do not pay; wait for NStack), held for review (`late_payment`/`mismatch`, quote reference shown, contact inviter or support) and ended. A copy, wallet hand-off or quote `settled` state is never shown as paid: only the credited list from `GET /topups` is.
